# Comment composer and review action menu

## Problem and scope

The proposal viewer discussion composer currently places a native state select beside a submit button labelled Approve. The label suggests approval even when another state is selected, making the review action ambiguous at submission time.

Secondary Markdown controls also have the same visual weight as the primary comment and review actions. The composer requires a compact, keyboard accessible interaction with one explicit comment action and one proper review action menu.

This decision covers the composer toolbar, review action menu, pending state behavior, and the relationship between the active revision and its discussion thread. It does not change review permissions, proposal storage, Markdown syntax, or server side state rules.

## Design decision

The composer has two primary actions: Comment and Review.

Comment is a normal submit button for a discussion message. Review is a real menu button, not a select styled as a button. Its closed label remains Review, so it never falsely claims that approval is selected.

The review menu contains exactly these actions:

| Menu action | Submitted state | Comment requirement |
| --- | --- | --- |
| Approve | approved | Required review comment |
| Reject with comment | rejected-with-comment | Required |
| Reject as complex or misformatted | rejected-complex-or-misformatted | Required |
| Reject | rejected | Required review comment |

Choosing an action submits the existing review request with the corresponding state. Empty review comments are rejected before submission and by the server boundary.

The review menu is available only while the active thread state is pending. For a non-pending thread, Comment remains available and the review menu is absent.

## Composer toolbar

Bold and Italic remain visible as frequent formatting actions. Quote, Code, Link, and Preview are grouped under a More disclosure control. More is never a submission control. Opening or closing it cannot submit the form.

The editor remains Markdown backed. Toolbar operations modify selected text, and Preview renders the same Markdown that will be stored. Quoting and persistent link conventions remain available through the existing Markdown editor.

## Revision and thread behavior

The page represents one proposal thread. The latest revision is the active document and supplies the thread effective state. Older revisions remain addressable for history but cannot present an active review action after a newer revision is submitted.

The diff from the preceding revision remains available as an explicit disclosure and is collapsed by default. The latest revision review state is shown in metadata, the discovery row, and action availability.

## Interaction and accessibility contract

The review control MUST:

- expose aria-haspopup with the value menu and aria-expanded;
- open and close with mouse, Enter, and Space;
- support Arrow Up, Arrow Down, Home, End, and Escape while open;
- place focus on the first menu item when opened;
- return focus to the trigger after selection or Escape;
- close when focus leaves the menu or the user clicks outside; and
- provide visible focus styling without relying on color alone.

Each menu item MUST have an unambiguous accessible name and MUST submit exactly one review action. The closed trigger MUST NOT contain a state specific label such as Approve.

The composer MUST remain usable without JavaScript for ordinary comments. JavaScript enhances the review menu and Markdown toolbar. The server remains responsible for validating the submitted state and comment.

## Visual language

Use the existing restrained proposal viewer language: white message surface, thin neutral border, compact sans serif controls, and serif reading content. Rejection actions MAY use a warning accent, but approval and rejection MUST remain distinguishable by text and iconography rather than color alone.

The menu aligns to the review trigger, remains within the viewport on narrow screens, and does not obscure editor validation. The primary action row places Comment before Review.

## Invariants

1. Comment creates a discussion message and does not change review state.
2. A review menu action creates one human review event and requires a non-empty comment.
3. The displayed review state always belongs to the latest active revision.
4. A superseded revision cannot be reviewed from active thread controls.
5. Formatting disclosures never submit the form.
6. The human only review boundary remains unchanged.

## Validation criteria

The accepted design MUST demonstrate:

1. The closed review control reads Review and never implies a selected outcome.
2. All four review actions are available from one keyboard accessible menu.
3. Each action submits the correct state exactly once.
4. Empty review comments are rejected before submission and by the server boundary.
5. Comment remains distinct from review actions.
6. Older revisions show history only and cannot expose active review actions after a newer revision is submitted.
7. The latest revision controls visible state and action availability on both proposal and discovery pages.
8. The diff disclosure is collapsed on first render.
9. Secondary Markdown controls are hidden under More while remaining keyboard reachable.
10. The interaction works at narrow viewport widths and with keyboard only navigation.

## Execution boundary

This is one proposal viewer UI decision with no prerequisite paper. The composer and review control implementation MUST remain gated by human approval of this paper.

## Risks and alternatives

A custom menu adds keyboard and focus management obligations that a native select provides automatically. The native select is rejected because it separates the selected state from the action label and permits the misleading approval presentation. Separate visible buttons for all review outcomes are rejected because they increase visual noise and make rejection choices appear equivalent to ordinary commenting.
