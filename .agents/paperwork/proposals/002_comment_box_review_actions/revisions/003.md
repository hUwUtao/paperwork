# Comment composer and review action menu

## Problem and scope

The proposal viewer discussion composer currently places a native state select beside a submit button labelled Approve. The label suggests approval even when another state is selected. The layout also does not define which controls remain in document flow and which controls float over it.

This decision defines the composer regions, menu anchoring, review actions, and active revision behavior. It does not change review permissions, proposal storage, Markdown syntax, or server side state rules.

## Design decision

The composer has four vertical regions in this order:

1. A formatting row with Bold, Italic, and More.
2. A full width Markdown editor.
3. A validation message region reserved below the editor.
4. An action row aligned to the end with Comment followed by Review.

Comment is a normal submit button for a discussion message. Review is a real menu button, not a select styled as a button. Its closed label is Review and never names a selected outcome.

The review menu contains exactly these actions:

| Menu action | Submitted state | Comment requirement |
| --- | --- | --- |
| Approve | approved | Required review comment |
| Reject with comment | rejected-with-comment | Required |
| Reject as complex or misformatted | rejected-complex-or-misformatted | Required |
| Reject | rejected | Required review comment |

Choosing an action submits the existing review request with the corresponding state. Empty review comments are rejected before submission and by the server boundary.

The review menu is available only while the active thread state is pending. For a non-pending thread, Comment remains available and Review is absent.

## Flow and floating behavior

The messagebox, toolbar, editor, validation region, and action row remain in normal document flow. Opening either menu MUST NOT change the height of the messagebox or move the editor and action row.

The More menu is positioned below its toolbar trigger and aligned to the trigger start edge. The Review menu is positioned above its action trigger and aligned to the trigger end edge. Both menus are positioned relative to their owning trigger container and use an overlay layer above the messagebox content.

Each menu has a maximum width of 320 pixels. If the preferred position would leave the viewport, the menu flips to the opposite vertical side and clamps its horizontal position inside the viewport with a 12 pixel margin. On narrow screens, the menu width becomes the available viewport width minus 24 pixels.

Clicking outside a menu closes it. Opening one menu closes the other. Menu dismissal does not alter editor text or submit the form.

## Composer toolbar

Bold and Italic remain visible as frequent formatting actions. Quote, Code, Link, and Preview are grouped under More. More is a disclosure control and never a submission control.

The editor remains Markdown backed. Toolbar operations modify selected text, and Preview renders the same Markdown that will be stored. Quoting and persistent link conventions remain available through the existing Markdown editor.

## Revision and thread behavior

The page represents one proposal thread. The latest revision is the active document and supplies the thread effective state. Older revisions remain addressable for history but cannot present an active review action after a newer revision is submitted.

The diff from the preceding revision remains available as an explicit disclosure and is collapsed by default. The latest revision review state is shown in metadata, the discovery row, and action availability.

## Interaction and accessibility contract

The Review and More controls MUST:

- expose aria-haspopup with the value menu and aria-expanded;
- open and close with mouse, Enter, and Space;
- support Arrow Up, Arrow Down, Home, End, and Escape while open;
- place focus on the first menu item when opened;
- return focus to the trigger after selection or Escape;
- close when focus leaves the menu or the user clicks outside; and
- provide visible focus styling without relying on color alone.

Each review menu item MUST have an unambiguous accessible name and MUST submit exactly one review action. The closed Review control MUST NOT contain a state specific label such as Approve.

The composer MUST remain usable without JavaScript for ordinary comments. JavaScript enhances menu behavior and Markdown tools. The server remains responsible for validating the submitted state and comment.

## Invariants

1. Comment creates a discussion message and does not change review state.
2. A review menu action creates one human review event and requires a non-empty comment.
3. The displayed review state always belongs to the latest active revision.
4. A superseded revision cannot be reviewed from active thread controls.
5. Opening or closing a menu never submits the form.
6. Opening a menu never moves the editor or action row in document flow.
7. The human only review boundary remains unchanged.

## Validation criteria

The accepted design MUST demonstrate:

1. The composer renders the four regions in the specified order.
2. Opening a menu does not change the messagebox height or move the editor.
3. More opens below its trigger and Review opens above its trigger at normal width.
4. Each menu flips or clamps correctly near every viewport edge.
5. The coded PNG sample is included with the proposal and matches the layout decision.
6. All four review actions are available from one keyboard accessible menu.
7. Each review action submits the correct state exactly once.
8. Empty review comments are rejected before submission and by the server boundary.
9. Older revisions cannot expose active review actions after a newer revision is submitted.
10. The diff disclosure is collapsed on first render.
11. The interaction works at narrow viewport widths and with keyboard only navigation.

## Execution boundary

This is one proposal viewer UI decision with no prerequisite paper. The composer and review control implementation MUST remain gated by human approval of this paper.

## Risks and alternatives

A custom floating menu adds keyboard, focus, collision, and viewport management obligations that a native select provides automatically. The native select is rejected because it separates the selected state from the action label and permits the misleading approval presentation. Inline menus are rejected because they move the editor and action row when opened. Separate visible buttons for all review outcomes are rejected because they increase visual noise.
